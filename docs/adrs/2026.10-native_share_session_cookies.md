# ADR: Allow secure session cookies on native share POSTs

Date: 2026-10-26  
Status: accepted

## Context

The installed app receives shared files through a top-level multipart POST. A
`SameSite=Lax` session cookie can be omitted on this navigation. The router then
redirects to sign-in without processing the files. The following GET includes the
cookie and redirects the already signed-in user to the dashboard instead.

## Decision

Use `SameSite=None; Secure; HttpOnly` for production session cookies. Retain
`SameSite=Lax` for explicitly allowed insecure development cookies because browsers
reject `SameSite=None` without `Secure`.

Reissue cookie attributes on authenticated requests, including fresh and temporary
sessions, without extending their lifetimes or updating session records unless
ordinary renewal is due. This migrates existing installed apps when reopened.

Keep `http.CrossOriginProtection` on the complete server handler chain. Do not add
a CSRF bypass or make the share upload endpoint public.

## Rationale

The native share target needs the session on its initial POST. Updating the cookie
policy fixes authentication without staging anonymous uploads or adding a service
worker transport. Server-side cross-origin checks remain the CSRF protection.

## Consequences

- Native shares can reach the existing authenticated, streaming upload handler.
- Existing sessions adopt the policy after an ordinary authenticated app request.
- Cookies can accompany cross-site requests; the Lax defence-in-depth is removed.
  Unsafe browser requests must continue to be rejected by cross-origin protection;
  safe HTTP methods must not mutate business state.
- Authenticated responses reissue a cookie even when expiry renewal is not due.
- Native sharing still requires HTTPS and a valid session. Insecure development
  retains the browser's Lax limitations.
