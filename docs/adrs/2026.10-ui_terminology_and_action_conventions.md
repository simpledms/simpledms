# ADR: UI terminology and action conventions

Date: 2026-10-04  
Status: accepted

## Context

A UI review found the same concepts named and presented in several ways: folder and directory,
field and property, organization and tenant, log in and sign in, mixed casing of Space and Inbox,
generic "Save" buttons on create or destructive dialogs, generic "Are you sure?" confirmations,
and duplicated create entry points on management lists.

## Decision

- User-facing text uses Folder, Field, Organization, Sign in, and app. Space and Inbox are always
  capitalized product terms. Tag kinds are named super tag and simple tag.
- New entities are created ("Create …"); existing things are attached ("Add field", "Add note")
  or linked ("Assign …").
- Dialog submit buttons name the action ("Create", "Assign", "Move", "Unzip"). "Save" is reserved
  for editing existing data.
- Confirmations name the object and the consequence ("Delete this tag? It will be unassigned from
  all files."). Reversible actions such as restoring from the Trash do not confirm.
- Management pages offer one create entry point: the FAB, plus an EmptyState action when the list
  is empty. Helper rows remain only inside dialogs and nested lists, such as tag group children
  and per-Space credential tabs where they preset the destination.
- List rows expose actions only through `ListItem.ContextMenu`; menu items use leading icons.
- Page titles omit the organization or Space name, which the navigation rail already shows.
- Dates use `timex` with the visitor language; inline metadata uses "Label: value".
- Buttons: tonal for the primary action of a group, outlined for secondary and destructive
  actions; elevated buttons are not used.

## Rationale

One term and one interaction pattern per concept reduces ambiguity, keeps translations stable,
and matches Material 3 guidance on button emphasis and empty states.

## Consequences

Users see consistent wording and behavior across Files, Inbox, Trash, and management pages.
Changed English strings changed their translation keys; affected de/fr/it entries were migrated
or retranslated and are marked fuzzy for review. Form labels derived from struct field names (for
example "Add me as space owner") keep their generated casing. MCP tool descriptions and internal
identifiers keep "directory" and "tenant", since they are API terms rather than UI text.
