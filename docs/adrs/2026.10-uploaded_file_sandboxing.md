# ADR: Sandbox uploaded files served from the application origin

Date: 2026-10-03  
Status: accepted

## Context

Downloads and inline previews (`?inline=1`) are served from the same origin as the
application, with the type detected from the file's content. A Space member could upload
HTML or SVG containing scripts. When another user, for example a tenant owner, opened
it inline, the script ran with that user's session. Same-origin requests also pass
`CrossOriginProtection`, so the script could call any command.

## Decision

Every handler that serves uploaded bytes (downloads, trash downloads, PDF previews, HTML
source previews) uses `SetDownloadSecurityHeaders`, which sends
`X-Content-Type-Options: nosniff` and `Content-Security-Policy: sandbox`. Inline PDFs
are the only exception. All other responses also send `X-Frame-Options: SAMEORIGIN`
and `nosniff` by default.

## Rationale

`sandbox` gives the document an opaque origin and disables scripts, forms, and popups,
while images, audio, video, and text still render. Chromium refuses to render PDFs in
sandboxed documents, and its PDF viewer cannot run scripts with access to the
application origin. A separate download domain would isolate files completely, but it
needs extra deployment configuration and signed cross-origin URLs, which self-hosted
installations would struggle with.

## Consequences

- Benefit: stored XSS through uploaded files is closed, whichever upload channel was
  used (browser, WebDAV, MCP, URL import, archive extraction).
- Drawback: HTML files shown inline render without scripts or interactive forms. The
  HTML source tab was already served as sandboxed plain text.
- Drawback: The PDF exception relies on browser PDF viewers staying isolated from the
  page origin.
- Revisit if downloads move to a separate origin.
