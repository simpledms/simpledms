# ADR: Preserve synchronized FTS indexes during tenant migrations

Date: 2026-10-23
Status: accepted

## Context

Ent does not manage the external-content FTS5 table or its triggers. Tenant startup
previously rebuilt the whole search index even without pending migrations, and every
file update retokenized its OCR text.

## Decision

Keep the FTS table across migrations. Drop dependent SQL views only before pending
production migrations (or development schema reconciliation). Reconcile the expected
view, FTS table, and trigger definitions transactionally afterwards. Rebuild FTS when
its table definition changes or a trigger is missing; otherwise update changed trigger
definitions without rebuilding the index. Missing triggers require a rebuild because
writes may have been missed, including during Atlas table replacement.

Only changed indexed text or row IDs trigger FTS updates. Space, Inbox, and directory
flags remain unindexed external-content columns and reflect the source table directly.

## Rationale

SQLite preserves the external-content virtual table when Atlas replaces the content
table, but removes that content table's triggers. Inspecting those objects avoids an
additional version ledger and retains repair-on-startup behavior.

## Consequences

- No full reindex on ordinary restarts or unrelated/index-only schema migrations.
- Metadata-only and unchanged text updates avoid unnecessary OCR tokenization.
- Reconciliation needs SQLite schema inspection and a short write transaction.
- Missing triggers and content-table replacements still require a full rebuild.
- Trigger-only upgrades assume the previous installed triggers maintained a synchronized
  index; missing objects are treated as requiring repair instead.
