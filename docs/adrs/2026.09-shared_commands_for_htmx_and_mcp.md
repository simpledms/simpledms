# ADR: Share model operations between HTMX and MCP

Date: 2026-09-18  
Status: proposed

## Context

SimpleDMS needs an MCP interface to existing document operations. Current HTTP actions mix
transport binding, presentation, and, in some cases, business decisions. Several model services
already provide reusable operations. Router wrappers provide important context, authorization,
transaction, and error-handling behavior that a second transport also needs.

## Decision

Keep the modular monolith. Add a typed MCP adapter using the official Go SDK and Streamable HTTP
inside the existing server. Both adapters call existing model methods, extracting remaining
business decisions from HTTP handlers only as their operations are exposed.

Extract reusable context/transaction execution from the router into a concrete shared executor.
Retain browser wrappers and presentation behavior. Register MCP tools explicitly, with public-ID
contracts and separate transport result mapping.

Use the [feature specification](../features/2026.09-mcp_server/spec.md) for scope and recorded
assumptions. Initial clients configure Space-scoped bearer credentials; OAuth onboarding is later.

Include a bounded native `upload_file` tool in the first release, reusing prepare/upload/finalize.
Its base64 payload and explicit size ceiling give clients a complete tool without an additional
HTTP transfer service. Add streaming transfers only when larger-file support is required.

## Rationale

This follows existing model, `Infra`, and Ent conventions. A direct Go call is the smallest reuse
mechanism. HTTP replay would couple tools to cookies, HTMX state, redirects, and HTML. Automatic
exposure of all `Actionable` objects would publish presentation operations and unsuitable commands.
A command bus, separate MCP service, or repository-wide command rewrite adds no necessary value.

## Consequences

Benefits:

- One implementation of business behavior and one shared execution lifecycle.
- Existing browser features can be migrated incrementally.
- MCP wire behavior and schemas are handled by a maintained SDK.

Tradeoffs:

- Small transport adapters and explicit registrations must be maintained.
- Some query/command extraction and public-ID migrations are prerequisites for richer tools.
- The existing context/error types retain some HTTP/UI coupling during incremental adoption.
- Native upload retains a bounded encoded JSON string and adds base64 overhead. Its size ceiling
  is lower than some installations' browser upload limit; it is not a general streaming API.
- Credential issuance, client authentication compatibility, and commit-before-response behavior
  require implementation work; adding an SDK alone does not provide them.
