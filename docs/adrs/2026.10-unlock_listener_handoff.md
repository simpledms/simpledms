# Keep the HTTP listener open during unlock

- Date: 2026-10-23
- Status: accepted

## Context

Unlock previously shut down the maintenance listener before runtime initialization
and tenant migrations. Reverse proxies returned 502 during this gap. SaaS wrappers
also need to register their routes after `Prepare` and before serving the app.

## Decision

Keep the maintenance HTTP server running after unlock. Signal identity readiness
to `Prepare` through a channel, and switch its synchronized handler only when
`PreparedServer.Start` is called. Use the same listener for HTTP, certificate TLS,
and autocert TLS. Stop it and close databases if preparation fails.

Browser polling retries server errors even when they lack the maintenance marker.
Marker-free client errors remain valid navigation destinations (for example, 404).

The maintenance handler owns an atomic state: locked, unlocking, or starting.
Claim unlocking before identity decryption; switch to starting after loading the
identity and before notifying startup. Both active states hide the unlock form,
including on reload with `?unlock`, and reject further unlock commands with HTTP
409. Failed attempts return to locked so the operator can retry. Read and validate
request bodies before claiming unlock so an incomplete upload cannot block it.
Maintenance pages are not cached; a stale form receiving 409 reloads the
server-rendered state. Each page snapshots the state once to render consistent form
visibility and localized status: "Unlocking application. Please wait." or
"Application unlocked. Starting up."

## Rationale

Switching handlers preserves connections and listener ownership while keeping
partially initialized application routes inaccessible.

## Consequences

- Unlock and initialization no longer create a connection-refused window.
- Existing maintenance requests finish with their original handler.
- Locked instances keep a live maintenance server between `Prepare` and `Start`.
- Handler access requires synchronization; initialization failure must stop the
  listener before closing its databases.
- Polling also waits when the destination itself returns an application 5xx error.
- Only one request can decrypt the identity at a time. Concurrent operators must
  wait for a failed attempt to finish before retrying; after success, the unlock
  form stays hidden and reloads use the existing 60-second maintenance refresh.
