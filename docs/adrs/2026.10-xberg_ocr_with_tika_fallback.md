# ADR: Xberg as OCR backend with Tika fallback

Date: 2026-10-08  
Status: proposed

## Context

OCR and text extraction ran only on Apache Tika. [Xberg](https://github.com/xberg-io/xberg)
offers an HTTP API (`POST /extract`) with Tesseract OCR and native extractors for many
formats, but it does not support every format that Tika parses.

With its defaults, Xberg 1.3.6 was not acceptable for a DMS:

- It silently adds a PaddleOCR fallback stage, which downloads models from Hugging Face on
  first use and recognizes only one language per run.
- Its Tesseract markdown output runs a non-configurable dictionary filter that drops lines
  dominated by unknown words. A scan reading "Xberg Scan Quokka 4711" returned no text.

## Decision

Admins can configure an Xberg URL (`SIMPLEDMS_OCR_XBERG_URL`) next to the Tika URL. If
Xberg is configured, it extracts text first. Tika is used if Xberg reports
`unsupported_format` or returns empty text, and a Tika URL is configured. If only Tika is
configured, behavior is unchanged. The fallback rule lives in `ocr.TextExtractor`.

Every Xberg request asks for markdown and pins OCR to a single Tesseract pipeline stage with
plain text output. Xberg's markdown is stored with its line breaks, so tables stay readable;
Tika's text is still joined into a single line.

The Compose files use the smaller `core` image pinned to `1.3.6-core` and set
`HF_HUB_OFFLINE=1`.

## Rationale

The pinned stage avoids both PaddleOCR and the dictionary filter while keeping Tesseract
with all configured languages. `HF_HUB_OFFLINE=1` turns any remaining model download into
a skipped stage instead of outbound traffic. Preloading the PaddleOCR models was
considered, but its single-language recognition would still drop German, French, and
Italian text.

Falling back only for unsupported formats and empty results keeps the extracted text
predictable: an Xberg outage or a parsing error leads to the existing OCR retry instead of
silently switching engines. Format support is discovered from Xberg's response instead of
its `/formats` list, so no format table has to be kept in sync.

## Consequences

- Benefit: admins can pick Xberg without losing coverage for formats only Tika handles.
- Benefit: Xberg runs without internet access and needs no model storage.
- Benefit: no schema or retry changes for files; the stored OCR content is the same field.
- Benefit: tables survive extraction, and MCP clients receive them as markdown.
- Drawback: stored OCR content is markdown for Xberg and a single line for Tika. Existing
  content keeps its format until OCR runs again.
- Drawback: files that fall back are downloaded from storage twice, and genuinely blank
  documents are processed by both engines.
- Drawback: with Xberg only, unsupported files fail and are retried up to the normal retry
  limit before OCR gives up.
- Drawback: Xberg rejects unknown options, so an upgrade that renames one breaks OCR.
  Upgrades must update the image pin deliberately and recheck the options, especially if
  the dictionary filter becomes configurable.
